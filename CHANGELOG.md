# Changelog

All notable changes to Uncoil are recorded here.

Uncoil follows [Semantic Versioning](https://semver.org). The `0.x` series *is*
the beta: features bump the minor, fixes bump the patch, and `1.0.0` will be the
statement that the app is out of beta. Each released section's body is used
verbatim as the GitHub Release notes and as the in-app update notes, so the
release notes are written once, here.

Uncoil has two update channels and one history. A **Stable** release opens a
`## [x.y.z] - DATE` section; an **Edge** release — a build published before
acceptance, to people who chose Edge in Settings › About — opens
`## [x.y.z-edge.BUILD] - DATE`. Work in progress accumulates under
`## Unreleased` until one of the two claims it. When an Edge line is promoted
to Stable, its sections are folded into the one stable section that release
publishes: the Edge headings are how a build was announced, not a second
history to maintain. The website lists the stable sections at `/releases/` and
the Edge builds at `/edge/`, straight from the signed feed.

## Unreleased

### Added

- Claude Code's own sub-agents are tracked. While sub-agents it started are still working, the session shows **Sub-agents working** instead of Ready, and "Turn done" waits until the last one finishes.
- A project can turn each notification event on or off for itself, or leave it to the app setting.
- The task list groups tasks by file when it shows every TODO.md, and the new-task picker names each file by its path.
- **SSH Hosts** (Settings > Integrations): import hosts from `~/.ssh/config` (Includes followed), add your own (written to `~/.ssh/uncoil_config`, reachable after a one-time, confirmed `Include` line), and open a plain `ssh` terminal on any of them.
- **Remote hosts per project.** Pick which SSH hosts a project uses from its settings (new **Remote Hosts** tab, with a link to the full list) or its overview panel. Agents started in the project are told only those hosts — Claude via `--append-system-prompt`, Codex via `developer_instructions` — and `uncoil_projects {"action":"context"}` returns the current list to a running session. A project with no hosts adds nothing to its agents' context.
- **Rename a session** from its sidebar context menu (**Rename…**). A name you give is kept — the first prompt no longer overwrites it — and clearing it hands the session back to automatic naming.
- **Import sessions** from Claude Code and Codex (project context menu > **Import Sessions…**). Uncoil lists the conversations those CLIs already keep for the project — in `~/.claude`, `~/.codex` and each account profile's config folder, held in the project folder or one of its git worktrees — with their own titles and dates. The ones you pick arrive as sleeping sessions; waking one resumes the conversation. Nothing is copied, and a conversation is never imported twice.
- **Shorter session lists in the sidebar.** Each project shows its 5 most recently used sessions (pinned ones always, and the one you have open), and a **Load more** row reveals the next ones; **Show less** folds the list back to its first page. Groups page on their own. Change the number, or show all, in Settings > General > Sidebar.

### Fixed

- A closed or sleeping session no longer flips back to Running when a late status report from its agent arrives. Only relaunching or waking a session brings it back.
- Restarting a Codex session resumes its conversation instead of sometimes starting fresh.
- A Codex session reopened mid-turn shows what it is doing, and a finished Codex turn sends "Turn done".
- Long Claude sessions open faster: the agent starts while earlier turns load, and only the end of the transcript is read.
- The task screen no longer stutters with many tasks while agents are working.
- The open-task badge stays legible at 99+.
- Clicking Settings while its badge shows opens the page the badge is about, and the trail is marked down to the agent with the update.
- Project settings list each MCP server and skill once, say which agents have it, and an agent's tab shows only its own.
- A session started in a folded project opens the project, so its other sessions stay visible.
- The project launcher no longer appears under a click aimed at the project.

## [0.2.0-edge.6] - 2026-10-23

First published Edge package, including the current 0.2.0 development line and the pending Uncoil Auto/Codex work.

### Fixed

- Updating or switching channels preserves compatible settings and completed setup even when newer agent profiles or preferences are present. Unrecognized values are retained, incompatible settings are backed up before conversion, and unreadable settings are never replaced with startup defaults.
- Selecting a channel immediately checks that channel for an available package.

### Added

- Settings › About chooses which updates Uncoil offers you. Stable is what
  every installation gets and stays on unless you say otherwise; Edge receives
  a release as soon as it is cut, before it has been through acceptance, and
  says so beside the picker. Switching back to Stable waits for the next
  Stable release rather than putting an older build over the newer one, and
  the choice cannot be changed while an update is being installed. The page
  also says which channel the copy you are running came from.

- Uncoil knows where its own updates come from. The release pipeline now
  produces a package that carries its channel, its version and its build, and
  refuses to be published as anything else: a bundle whose Info.plist, git tag
  and release notes disagree never reaches a feed. Each channel is generated
  from its own packages only, every enclosure is checked against the key the
  app ships with, and the website verifies after every deploy that the package
  a feed advertises can actually be downloaded at the length it claims.

- Agents in Uncoil can direct other agents by meaning rather than by keystroke. Through Uncoil's MCP tools an agent can ask what a session supports, read its conversation as a structured timeline, follow it event by event — waiting for the next one instead of polling terminal output — submit a prompt, interrupt a turn, and resume a stopped session back in its conversation. The same calls work for a structured Codex session and for an agent that is only a terminal; what differs is reported, not guessed from the agent's name. Answering another session's approval is a separate, opt-in grant, or a per-session permission you give, because it decides on your behalf that a command may run.
- An agent can start a session the way you do: choosing the agent, the account, the model, the effort, the working mode, the project or worktree, and the first prompt. Choices the installed CLI does not offer are refused rather than passed along to fail, a plain shell is never started this way, and the new session can never hold more permissions than the agent that started it. A new `uncoil_agents` tool lists the agents installed, their accounts and what each one offers, and `uncoil_system describe` reports the whole control-plane contract — versions, every action and whether it only reads, and every error code.
- Claude can run as a structured session, the way Codex can. With `-claude-structured`, a Claude session speaks Claude Code's own JSON interface instead of driving its terminal: its replies, commands, file edits and tool calls arrive as the same structured timeline Codex sessions have, its permission prompts are answered in Uncoil's approval panel, and other agents can submit to it, interrupt it and follow it through the control plane exactly as they do Codex. Approving a tool "for this session" stays in the session — it never writes a rule into the project's Claude settings. A session that cannot start this way falls back to the ordinary Claude terminal, and a resumed session shows its earlier conversation. Still opt-in: it gives up Claude's own prompt and slash commands until Uncoil has its own.
- A call an agent retries runs once. An action sent with an idempotency key returns its first answer to a retry, so an agent that timed out and asked again cannot submit the same prompt, or answer the same approval, twice.
- Uncoil Auto: a session of Uncoil's own, started from Quick Launch like an agent, from which a project's agents are directed. Name an agent with `@` and the prompt is typed into that agent's own terminal; name two and both get it; name one that has no session yet and it is started. What each agent then says and does — replies, commands, edits with their diffs, tool calls — comes back into the conversation under the agent's name, read from the transcript the CLI already keeps, so Claude Code, Codex and the rest run exactly as before and nothing stands between you and them. Addressing an agent after another one answered hands it that answer as context, which is how agents hear each other. Beside the conversation, every agent in the project shows its state, what it last did and how much of its limit is left; clicking one — or an agent's name in the conversation — opens its own terminal in a window. Typing `@` or `/` opens completions above the field: agents, Uncoil Auto's commands (`/new`, `/stop`, `/agents`, `/clear`, `/help`), and after `@agent /` that agent's own commands. The conversation is kept across launches and picks up where it was: what the agents did while Uncoil was closed is read from their transcripts and added in place, marked as such. A prompt that names nobody goes to the agent on the round button beside the field — the only agent when there is one, the newest otherwise — and stays with it until you pick another; an `@mention` sends one message elsewhere without moving it.
- Uncoil Auto has its own page under Settings › Agents. It chooses which agents a conversation can reach — a conversation can narrow that further from its agents panel, never widen it — and an agent that is not open to it cannot be addressed or started from there. The session header says whether the control plane is up, and each agent in the panel shows its own MCP link. Agents a conversation is directing no longer notify while you are looking at that conversation, which already shows their replies and waits; the page can set this to notify as usual, or to only permission requests. Sessions outside Uncoil Auto notify exactly as before.
- Edge: Auto runs in Uncoil Auto. `/auto <task>` — or, if you choose so in Settings, any message that names no agent — runs the task with the conversation's agent as Main and brings in specialists around it, each in a session of its own that you can open from the conversation or the agents panel: an Explorer that reads the repository so its search stays out of Main's context, a Researcher for documentation and release notes, a Worker that implements Main's brief in its own worktree, and an Advisor — Fable by default — for a deep second opinion before the plan, on a repeated failure and, if you like, before completion. Specialists hand back a structured result rather than their whole conversation. After every Worker turn the project's own test suite is run, and a run is complete only on that evidence, not on the Worker's word; a run with nothing to verify with says so. Retries, repeated-failure thresholds, budgets and time limits are policies, and every agent keeps its own approvals. Small control decisions — whether research is needed, what to do with a failure, whether a finished change deserves a review — can be put to Laya, a local System 1 decision model managed from the settings page; each decision starts in shadow mode, where Laya's answer is recorded but the policy acts, and can be made active one at a time. A diagnostics view shows every step of a run, every decision with Laya's probabilities and what the policy did, and every verification with its output. Settings › Uncoil Auto configures it all — the agent, account, model and effort of each role, set one by one, and the checkpoints, policies and limits.

### Changed

- The Session Presets editor is gone. A preset is a role — what a child session started by an agent through `create_child` is allowed to do — and editing roles by hand asked you to design a permission model before you could use the app. The built-in roles are the model now. A list written by an older build is still read and still honoured, so an existing setup keeps working.

- Settings separates what Uncoil connects to from what Uncoil is. GitHub and the Computer Use drivers are under Integrations — things you bring and can take away again — while the control plane, permissions and retention sit under Advanced. The Agent Status Hooks page is gone: installing those hooks is what Connect in the Agents list already does, and having it in two places meant one of them was always showing a stale answer.

- Notifications are one page. They were four — General, Events, Reminders, Quiet Hours — for a single decision: when should Uncoil interrupt you. Whether an event repeats is now set on the event itself, where its switch, priority and sound already are; it used to be a second list on the Reminders page, so the same value had two homes and one of them always looked out of date. Each event opens to show its own priority, sound and repeat, and stays a single switch until you need them.

- Settings has a page per agent. Setting up Codex used to mean visiting four pages — Installed Agents, Accounts, CLI Tools, Run Parameters, Working Mode — each one a table of every agent against a single setting, so three quarters of every page was about some other agent. Now the page is the agent: its logins, what it does without asking, the parameters its sessions start with, and the CLI Uncoil runs, in one place — opened from the row in the Agents list that already says whether that CLI was found. The sidebar is unchanged, because a row per agent would grow it with every CLI installed. Links and palette entries written against the old pages open the Agents list, which still says which CLIs were found and where they live.

- Quick Launch reaches every agent. The pill of agent marks over a project row now ends in a plus once the pointer is on it, and that opens the full list — the agents left out of your Quick Launch order, and the plain terminal, which until now could only be started from the command palette. The marks themselves are unchanged: one click starts that agent, right-click picks a second login.
- Clicking a project opens and closes it. The disclosure chevron is gone: it was an 8pt mark at the far edge of the row that had to be aimed at, and the row itself is the target now. A folded project opens when you click it, and the project you are already on folds away; arriving at a project from somewhere else only selects it, so getting to a project never hides what it is holding.
- A folded project still shows the session you are looking at. Folding one used to hide everything under it, including the session filling the rest of the window — so the sidebar could show no trace of the agent you were reading, and there was no row to click back to. That one row stays, whatever is folded.
- A session's actions are a menu, and the menu bar has one too. The session header had grown a square icon per verb, and none of them had a menu item or a keyboard shortcut, so restarting a session or opening its folder meant being at that header with a mouse. There is now a Session menu in the menu bar that acts on whatever is selected, and the same list behind the header's `...`. Two controls stayed in the header on purpose: the run button, because its colour is how you know the project's dev server is up and a menu you have to open is not a status, and the handoff button, which only appears when a login is about to stop your work.
- A project's settings are one sheet, beside the project. Customise gained a Notifications tab, so what a project may interrupt you for is decided where the project is rather than in a global settings pane that listed every project you have and made you find yours. The pane is gone; the sheet is Cmd-I, and there is now a Project menu in the menu bar carrying it, New Session and Open in Finder — verbs that until now existed only in the sidebar's right-click menu, with no shortcut and nothing to discover unless you thought to right-click.

- Control-plane calls are tied to the session that makes them. Each session is started with a token only Uncoil can issue, and a call is that session's only when the token matches; until now a session id alone was enough to act as that session. A session started before this update can still read, but has to be restarted before it can change anything.
- A prompt or interrupt sent to a session that is not running says so. It used to be typed into nothing and reported as sent.

### Fixed

- Codex sessions keep their conversation again. Since Codex 0.160 a thread is written to disk only after its first prompt, so Uncoil — which looked for it during the first half-minute — never learned which thread a session was in, and reopening it started over. Uncoil now reads the thread from the Codex process it started, the moment Codex opens it, and follows it when you switch thread from inside Codex with `/new` or `/resume`.
- Codex sessions show what Codex is doing — working, running a tool, done, interrupted — read from the thread Codex is writing, and take their name from Codex's own title for the thread.
- A Codex session is no longer named after the terminal's reply to a colour query (`10;rgb:e9e9/…`); sessions already named that way get their name back. Capitals and characters typed with Shift — `/` on a Turkish keyboard among them — are kept in a session's name when the agent uses the kitty keyboard protocol, and a bare `/model` or `/status` no longer names a session.
- Codex's "Approve for me" working mode starts Codex with its own `--approve-for-me`, which hands approvals to Codex's automatic reviewer, instead of turning approvals off.
- "Open in Finder" opens the project's folder instead of showing it selected in its parent. The editor menus — the project dashboard's, a session's `⋯` and the sidebar's — list every installed editor with its icon, and offer Xcode when the folder holds an Xcode workspace, project or Swift package, opening that rather than the bare folder.

- Uncoil Auto's conversation and its message field use Uncoil's own thin scroller instead of the system one, which came back whenever the transcript was rebuilt.
- Uncoil Auto's message field no longer shows the Writing Tools / Siri button: a prompt for an agent is not prose to rewrite.
- Shift+Enter inserts a clean newline in Codex, OpenCode, Grok, Hermes and Cursor. They took the backslash Claude Code expects as text — and in OpenCode the carriage return after it sent the prompt. They now get a line feed (⌃J).
- Option symbols type again with Option as Meta on. On Turkish, German and other layouts `@`, `#`, `[` and `|` live behind Option, and every one of them arrived as a Meta chord instead of the character.

- The Drivers page stops reporting a stale answer. Installing the Chromium runtime, or granting the Cua driver its macOS permissions, ended by re-probing the driver — but the probe refused to run while an action was in progress, and the action was still marked in progress when it asked. The page went on saying the runtime was missing until it was refreshed by hand. An installed driver now says where it is, which version answered, and — one row each — which macOS permissions it actually holds. The driver reports those in ticks and crosses; Uncoil reads that and says what it means, rather than pasting the tool's output onto the page.

- A session on an account profile no longer breaks Codex. Project extension
  scope was read from `~/.codex/config.toml` while the session launched with the
  account's own `CODEX_HOME`, so switching a server off named one the profile
  never declared — and Codex refused the whole config with `invalid transport`.
  The scope is now read from the config root the session actually uses.

- Restarting a session restarts it everywhere. The verb was written out at each surface that offered it, and the copies had drifted: restarting from the session header or a split pane rebuilt that one terminal view, while the command palette, the group view and Settings rebuilt every view of the session. So a restart from the header left the split pane, the popout and the group view still showing the process it had just killed. Closing and deleting a session were duplicated the same way, each copy deciding for itself whether the process was closed before the record went.
- A second window no longer restarts the app's services. Opening one with Cmd-N re-resolved every agent binary, asked every CLI for its version again, re-ran the cleanup of dropped images and reassigned the runtime daemon's session bookkeeping out from under the first window. The services the app has to start belong to the app; they now start once, whatever the windows do.

- Waiting on child sessions for longer than 30 seconds no longer always times out. Uncoil's MCP server gave up on every call after 30 seconds while `wait_for_children` waits two minutes by default, so the agent was told the wait had failed while Uncoil went on waiting for nobody. The server now waits as long as the call asked to, and cancelling a call in the agent now stops it in Uncoil too, instead of leaving it running out its clock.
- Starting an agent on a task through the control plane assigns the task to it. The session started, but the task was never linked to it, and the title given for it was ignored.

### Development

- Development is consolidated on `edge`, with the simplification state and daily worktree changes preserved in local backup tags. Release build allocation now advances beyond both Stable and Edge release tags, preventing a stable promotion from reusing an Edge build number, and a release now carries its channel in the bundle so a package can be identified independently of the preference selected in the app. The Edge feed itself is not published yet, so choosing Edge today finds nothing to install.

- The website serves the two channels. `uncoil.gokhantopbas.com` gained an
  Edge feed alongside the stable one, an `/edge/` page generated from that feed
  rather than written by hand, and a 404 page that says the address is wrong
  instead of implying the site is down — which matters on the host that also
  serves the update feed. The deploy asks both feeds the questions Sparkle will
  ask, plus one it cannot: whether the package each item points at exists.

- Release notes are still written once, but they now name a channel. A stable
  release opens `## [x.y.z]`, an Edge release `## [x.y.z-edge.BUILD]`, and the
  tooling reads the notes from the heading that matches the package it is about
  to publish. The `/releases/` page stays the stable history; Edge builds are
  listed on `/edge/` from the signed feed, so no second list has to be kept in
  step by hand.

## [0.2.0] - 2026-09-03

### Added

- Blueprints: the prompt you always write when you start a project of a certain shape, kept and named. Most people build the same shapes over and over — a workspace with `api/`, `web/` and `docs/` under it, the same three files at the root, the same opening instructions — and retype that paragraph every time. Write it once, and adding a folder offers it as a card. Uncoil creates nothing on disk itself, which is the point rather than a shortcut: whether `api/` should hold a Fastify skeleton or a Go module, and what *this* project's CLAUDE.md should say, is judgement, and judgement is what the agent is for — a tree stamped out by the app would still need all of it applied afterwards. A blueprint can also be applied to a project you already have, from its right-click menu or the command palette. Each one decides whether its prompt is sent the moment the session opens or typed in and left for you to read first; off is the default.
- A blueprint can be written by talking to an agent. "Write One With an Agent" opens a session whose only job is to interview you about how you actually work and then save the result — it is told not to invent a layout for you, because a blueprint its author does not recognise is worse than none. That session is the only one allowed to write blueprints: the grant is opt-in and belongs to the session you opened for it, since a blueprint is text a *later* session gets handed, and anything that could write one silently could leave instructions behind for a session that has not started yet. Anything an agent writes — or that you import from someone else — arrives as a draft that cannot start on its own until you have opened it and kept it.
- The new-project sheet asks the useful question first. It now opens centred on the window with the project's name and path at the top, a pencil that opens renaming and the icon and colour in place, and a row of cards: Default on the left, then your blueprints. The MCP and skill list moved behind one button, because "which setup is this?" is asked every time and "which of my MCP servers does this need?" is asked by people who have felt the cost of the answer being wrong. Cancel now removes the folder it just added, so a button that says Create can un-create.
- MCP servers and skills can be chosen per agent. A tab strip across the picker — All agents, then the agents from your Quick Launch list, terminal aside — lets one project give Codex a server it does not give Claude Code. Silence inherits: an agent with nothing to say about a server follows the all-agents rule, and an exception disappears again the moment it agrees with it. Exceptions are named on the All tab rather than hidden behind a tab nobody opens.
- A project decides which MCP servers and skills its agents get. An agent handed twenty servers and thirty skills pays for all of them in its context window before it reads a line of your code, and most of them have nothing to do with the project in front of it. Every project now has an "MCP & Skills" tab in Customize, and adding a folder asks the question once, up front. Nothing is written to your agent's own configuration — the choice is applied per session, at launch, through each CLI's own mechanism, so a session in one project can carry a different set from a session in another at the same moment. Everything is on until you turn it off, which means a project you never configure behaves exactly as it did before, and a server you install next week reaches every project that has not refused it. A change applies to the next session; one already running keeps what it started with, because no agent CLI can be told to reload this mid-conversation.
- Uncoil says which half of that it can actually deliver, per agent, rather than implying all of it. Codex scopes both servers and skills; Claude Code and OpenCode scope servers. Claude Code's skills are not scoped, and the screen says so where you are choosing them: the CLI has no per-session skill selection, and the two ways to fake one would each cost more than they save — one would drop the settings file Uncoil's own status hooks live in, so sessions would stop reporting themselves, and the other would take Uncoil's skills away from every `claude` you start outside the app. Agents with no per-session mechanism at all get no invented flags. Every entry in that table was read off the installed CLI, and a test holds the screen and the launcher to the same answer so the app cannot start claiming one thing while doing another.

- An agent's running sessions can be restarted together. Most agent CLIs read their configuration and their own code once, at launch, so a session that was already open keeps running the version it started with — Claude Code says so itself, asking to be restarted the moment it finishes updating. Doing that meant finding every session of that agent and restarting each by hand, which is exactly the list Uncoil already keeps. Settings › Agents › CLI Tools now offers it per agent, and offers it whenever that agent has something running rather than only after an update, because "restart it" is the answer to more than one question. Sleeping sessions are left asleep: hibernation already ended their process, so they come back on the new version when they are next opened, and waking them to restart them would undo the thing they were put to sleep for.
- A count in a red circle, on the corner of the control that leads to it. The settings button carries the first one — the number of agent CLIs with an update waiting — and it is a component rather than one button's decoration, because this is a shape the app will want again. It draws nothing at zero, so a caller can attach one unconditionally and let the number decide; it takes no layout space, so a rail of icons never shifts sideways when one of them has news; it grows into a capsule for two digits instead of squashing them and caps at 99; and the digit's colour is chosen from the fill's own brightness rather than fixed, because the meaning colours swap ends between the light and dark themes — the dark theme's red is a light rose, the light theme's a deep crimson, and white text is right on exactly one of them.

- The theme can follow your Mac. Settings › Theme and Colours now offers System, Light and Dark instead of two options, one of which was labelled "On" — a mistranslation of "Açık", which is Turkish for both *light* and *on*. On System, Uncoil switches when macOS does, at sunset or whenever you flip it. Switching appearance restores that theme's own colours, which was already true and is now said out loud under the picker.
- Themes cross over instead of snapping. Changing appearance repaints every surface in every window at once, and doing it on a single frame read as a glitch rather than as a setting taking effect; the interface now fades out, changes, and fades back in. Reduce Motion turns it off, as does the app's own animation switch.
- Hermes carries its own brand mark, drawn in the interface's own text colour. The mark ships with no colour of its own — it takes whatever it is drawn in — so that is what Uncoil does with it: light on the dark theme, dark on the light one, legible on both without a palette entry to get wrong.
- Hermes is an agent Uncoil runs. Its configuration is YAML rather than JSON or TOML, so Uncoil edits `~/.hermes/config.yaml` in place instead of reading and rewriting it: Hermes' own example config is over a thousand lines of commented documentation people copy from and edit, and a round trip through a parser would return it alphabetised, re-quoted and stripped of every comment that explained why a setting was there. Only the `mcp_servers:` entries Uncoil manages are touched; everything else comes back byte for byte. Accounts are kept apart with `HERMES_HOME`, which moves the whole Hermes home — config, credentials and session store together. Everything claimed for it was read off the installed CLI: `--resume` for waking a session, `-m` and `--reasoning` for the model and effort pickers (whose levels are read from the help text, so a Hermes release that adds one is followed automatically), `--yolo` for the one approval mode it documents, and `hermes update` for updating itself. Uncoil adds no flag it has not checked. Waking a session also passes `--no-restore-cwd`, because Hermes otherwise returns to the directory the session was recorded in and would quietly move the agent out of the worktree Uncoil started it in.
- Hermes reports what it is doing, the way Claude Code does. It is the only other agent with a real hook system, and Uncoil now speaks it: session state is read rather than guessed from the terminal, and a session names itself after the first thing you ask it. Connecting it writes the hooks into your own `config.yaml`, after a backup, touching nothing but its own entries — your hooks and the comments explaining them come back exactly as you wrote them. Hermes asks for consent once per hook before it will run one, so Uncoil records that consent for the six commands it just added, and for nothing else: it never turns on the setting that would approve every future hook from anyone. The events do not line up by name and were read off Hermes' own source instead — its `on_session_end` fires at the end of every *turn*, not of the session, and taking the name at face value would have marked every session finished after its first reply. One gap is worth knowing: Hermes has no event for stopping to ask you something, so a session waiting on one of its approval prompts is still read from the terminal.
- Uncoil can be told where an agent is. A fixed list of install locations cannot cover every way a CLI gets onto a Mac — nix, pipx, mise, a company image, an install kept on an external disk — so every row in Settings › Agents now has a "Locate…" button. Settings › Agents is the home for this — every row there has a "Locate…" button, installed or not — and the Extensions window's card offers the same thing so acting in either place is the same act. Point it at the executable or at the folder holding it and every part of the app believes you at once: the Agents list, session launch and the usage checks all ask the same question and now get the same answer. Nothing is copied or moved; the install stays exactly where it is. A location with nothing in it is refused rather than saved silently, and one that has gone away — an ejected disk — is said so in the row while the ordinary search carries on, so unplugging a drive never makes an agent you also installed normally vanish.
- Uncoil finds the agents on your Mac and says how well it can actually work with each one. Settings › Agents › Installed Agents lists every agent it knows — Claude Code, Codex, Gemini CLI, OpenCode, Grok, Cursor and Amp — whether it is installed, and which of four levels it is at: live events, control plane, terminal only, or found-but-nothing-more. The level is what is true rather than what sounds good: Claude Code reports session events through hooks, Codex and OpenCode load Uncoil's tools but send no events, and the rest are read from their terminal. Where Uncoil can close the gap itself — Claude Code's hooks missing, half-installed, or pointing at a helper that has moved — the row offers the one action that closes it, and "Connect all" does the lot. Each agent is judged against its own ceiling, so an agent that has no hook system to install is not marked as wanting one forever. The same list opens the Extensions window's Agents screen.
- OpenCode, Grok and Cursor are agents Uncoil runs. Each was checked against the installed CLI before anything was claimed for it: OpenCode takes Uncoil's MCP server through `OPENCODE_CONFIG_CONTENT`, which merges over your own config without writing to it, so its sessions reach the control plane with nothing to set up. Grok and Cursor have no per-session equivalent, so Uncoil reads their terminals and says so rather than advertising tools that would not answer. All three resume a conversation, take their own working modes — Grok's from `--permission-mode`, Cursor's from `--mode`, `--auto-review` and `--force` — and keep separate accounts in their own config roots (`GROK_HOME`, `CURSOR_CONFIG_DIR`). Uncoil adds no flag it has not read in the CLI's own help.
- Every agent has its own mark and colour, in the Extensions list and in Settings. Cursor and OpenCode come from Simple Icons; Amp and Grok from their vendors' published assets. A brand mark is not always square — Amp's is a wordmark twice as wide as it is tall — so the marks are drawn to their own proportions inside a fixed column, which keeps the names lined up without squashing the logo to fit.
- The Issues area is drawn from the same surfaces too: the issue and its labels in the head, the body, its assignees and the comment box in a drawer that only exists when it is open, and the one thing Uncoil can actually do about an issue — hand it to an agent — as the card's own action rather than one icon among four. The demo fixture now carries issues, run configurations and a repository of its own, so all three areas can be looked at without a network or an account.
- The Run area is drawn from the same surfaces the Tests screen is: a card whose head is the configuration and its one action — start, or stop — with everything that changes while it runs folded into the drawer beneath. A configuration that has never been started has no drawer at all. The status ring distinguishes a run that is *live* from a test that *passed*: both are green, but a dev server that is up is not a verdict, so it carries no tick. The five housekeeping controls are bare glyphs beside the one that matters, instead of five filled boxes that all looked equally important.
- The Tests screen moves. Opening a suite, switching a filter, a step arriving from a run in flight, a suite going from running to green — each of these changed the screen instantly and invisibly before, and each is now a transition on the app's own springs. A tally of zero is no longer a button: clicking it could only empty the list.
- A suite that is running shows how far it has to go, not just how far it has come. Frameworks that announce their plan — pytest's `collected 15 items`, cargo's `running 8 tests` — are read for it, and the rest fall back to the last run's total, which the fraction says out loud is an estimate. The fraction is also the control that shows every step, so the count of steps and the way to see all of them are one thing.
- The Tests screen is built from a set of shared surfaces rather than one screen's own layout: a status ring that distinguishes never-run from running from passed from failed, a card with a drawer tucked under it, a tally chip, a row with a status mark and its own rounded shape, and a summary bar that reads the same whether a run is in flight or finished. Each is a component in `App/UI/Components`, so the next screen that reports on long-lived work — runs, tasks, sessions — is drawn the same way instead of approximately the same way. A suite now leads with its name and one large action; how it went is folded into the drawer beneath, where the tallies double as the filter for the steps.
- The Tests screen says what a run did, step by step. A finished suite used to show its failing tests by name and nothing else — the reason was in the log tail, if it was anywhere. Every test the runner reported is now a row: what it was, whether it passed, was skipped or failed, and how long it took, with the failure message the runner actually printed sitting under the test it belongs to. Failures are what the list opens on, and a suite that came back red opens itself, because a run of four hundred green rows is exactly what hides the one red one. The chips above the list switch between all of them, and their counts are the rows they produce. Failure messages are read from XCTest, `swift test`, `go test`, `cargo test` and pytest; a framework whose failures Uncoil cannot read leaves the message empty rather than showing an unrelated line that happened to be nearby.
- A failing suite can be handed to an agent. "Fix with agent" on a red suite — or on one test, from its detail window — opens a new session on your default agent and settings, named after what is wrong, and hands it the failing names, the reasons the runner gave, the files the run wrote, and a note on the MCP actions that drive the suite: `test_run` to re-run it, `test_results` to read the last result, `test_list` and `test_update` for the configuration. A new session rather than whichever agent happened to be active: a failure is its own piece of work, and dropping it into a session halfway through something else buries both. The prompt tells the agent to decide first whether the test or the code is wrong and to say which, and not to weaken or delete an assertion to make it pass — a suite turned green by deleting what it was checking is worse than a red one.
- Maestro is a framework Uncoil reads, so mobile and web end-to-end flows report the same way unit tests do. A project with flows in `.maestro/` — or in `e2e/` or `flows/`, once a file there actually declares an `appId` or a `url` — gets a suite proposed for it, pointed at a screenshot directory inside the project rather than Maestro's own default under the home folder. Each command of a flow is a row of its own, under the flow it belongs to, with the reason a failed assertion gave underneath it and whatever the run drew alongside it: `Tap on "Sign in"`, not one line saying the flow failed. Maestro draws its output as a box on the terminal, so the frame and the colour codes come off before any of it is read. Running a flow still needs the `maestro` CLI on PATH and a device or browser it can reach — Uncoil runs the command, it does not install anything.
- A step opens onto the whole of it. A row can only ever show the first lines of a failure and the number of files a test produced; clicking one opens a window with the message in full and selectable, thumbnails of what it drew, and the run it belonged to — the command, the framework, the exit code, when it finished and what it came to.
- A suite that is running says what it is doing. The steps appear as the runner prints them — a count, the elapsed time, and the last few tests to report — so a suite that takes four minutes is watchable instead of a spinner over a log. What arrives live is read by the same parser that reads the finished run, so nothing changes shape when the suite ends; a framework whose output is not parsed still shows its output, which is all there is to show.
- A test suite can show what it drew. Give a suite an `artifacts` directory in `.uncoil/tests.json` — where it writes its screenshots, its recordings, its report — and the files it produced during the run are listed with it: images open in the app, everything else in whatever app owns it. A file whose name names a test is shown under that test, and one that names nothing is shown under the run. Only files written while the run was in flight count, so yesterday's screenshot is never attached to today's failure, and a path pointing outside the project is refused — the field is editable by agents.
- Sessions name themselves after the first thing you ask them. Until now only Claude did, through its hooks; every other agent — Codex, Gemini, a plain terminal — kept "new session" forever, because what you type goes straight from the keyboard to the terminal and the app never saw it. It sees it now, and the name is taken from your own words rather than from a model, so it costs no quota and works with nothing logged in. It happens once: a session keeps the name it was given, and a name that means something is never overwritten. Text Uncoil sends on its own account — a branch-change note, a repair prompt — never names anything.
- Uncoil updates itself. It checks `uncoil.gokhantopbas.com` once a day for a newer version, verifies what it downloads against a signature before installing it, and tells you only when there is something to install. "Check for Updates…" sits under the Uncoil menu for when you want to ask, and Settings › About can turn the automatic check off. Updates are only ever offered — nothing installs without you saying so.

### Fixed

- "Add Project" selects the folder you just added. It reached for the last project in the list, and the list keeps the Scratch workspace at the bottom, so anyone with a scratch folder got shown Scratch instead — and got shown the wrong project again when the folder was already open.
- Uncoil no longer dies when its background service goes away. The app talks to that service over a socket, and it is designed to expect the service to disappear — it is upgraded, it is ended after a stall, it crashes — which is why the sending code checks what the write came back with and reconnects. It never got to: writing to a socket whose other end has gone raises SIGPIPE, and a process that has not said otherwise is killed by it outright. The service had said otherwise on its own side and the app had not, so the very case the reconnection logic was written for was the case that ended the app instead. Both ends now ask for the error rather than the signal, which is what the code on both sides was already written to handle.

- Reopening a session goes back into the conversation, or says why it could not. Uncoil passed `--resume <id>` whenever it had an id, and an id is not a promise. Claude files each conversation under the working directory it was held in and prunes old ones, so a transcript it no longer had answered `No conversation found with session ID: …` and quit — the session opened onto one line of error and nothing else. Codex takes an exclusive writer lock per thread and refuses a second one, so any Codex process still running from an earlier Uncoil — one that outlived the app or its background service — made `codex resume` fail with `thread … already has an active writer`, which is why it "mostly just didn't work". Both are now asked before the flag is used: Claude's transcript is looked for where Claude actually keeps it (the directory-name rule was read off real installs, hyphen for hyphen, and a worktree has a directory of its own), and Codex's lock is tested rather than assumed. A conversation that is genuinely gone is forgotten rather than asked for again — a record still holding a dead id could never learn the id of the session that started in its place, so every later launch repeated the same failure — and the session says on its own status line that it started fresh, and which of the two reasons it was. A provider whose store Uncoil has not verified is resumed exactly as before: refusing a resume that would have worked is worse than the error it avoids.

- Codex sessions bind to the thread they actually started. Uncoil matched a new session to a transcript by file modification time and took the oldest — but a thread another agent is still working in is written to constantly, so the file times said nothing about which thread belonged to the session that had just launched. In a directory with two Codex sessions, which is the ordinary case in Uncoil, the new session could be bound to the other one's thread: resuming it later meant reopening somebody else's conversation, or being told the thread already had an active writer, which it did. The match is now made on the thread's own start time, taken from the transcript's first line, and the newest wins.

- Codex's permission mode is Codex's again. Every launch carried `--sandbox` and `--ask-for-approval` whether or not anyone had opened the setting, so whatever was configured in `~/.codex/config.toml` — or chosen inside Codex's own `/approvals` — was overruled every time, and there was no way to ask Uncoil to stop. There is now: "Provider default" is offered, and it is the default, for every agent. Uncoil adds no flag it was not asked for, and that has to include the flags nobody asked for by default. Read Only is a real mode rather than a label: it used to be quietly turned into Codex's workspace-write, which is to say the one mode whose name promises it cannot write was the one that could. The second code path — the app-server transport, which takes no command line and sends the same choice as two protocol fields — had drifted from the first and fell through to workspace-write for everything it did not name; both now come from one mapping, and on "provider default" it reads the user's own config file instead of substituting Uncoil's idea of a sensible pair. Every flag and every pair was launched against the installed CLI before being offered.

- Agent CLI updates work, and the ones that cannot are no longer offered. Every part of this was one mistake with several faces: the newest version was asked of npm no matter where the tool actually came from. Codex is installed here as a Homebrew cask; npm had published a version Homebrew had not, so Uncoil offered an update, ran `brew upgrade`, got nothing — and reported a failure for a tool that was in fact current. Each install is now asked of its own channel: Homebrew installs of `brew outdated`, npm and Volta installs of the registry, and Grok of itself, since `grok update --check --json` answers with the version it would install. Four fixes follow from the same reading. A cask upgrades with `brew upgrade --cask`, not `brew upgrade` — on a cask the latter looks for a formula by that name, finds none and stops. An npm update now puts its own Node first on `PATH` instead of merely naming its npm: npm is a script with a `#!/usr/bin/env node` line, so it runs under whichever node resolves first and takes its global prefix from *that* interpreter — measured here, nvm's own npm reported `/opt/homebrew/Cellar/node/26.0.0` as its prefix and would have installed Gemini into a Node that Gemini does not come from, exited 0, and left the version untouched. Everything Uncoil runs on your behalf now runs with the PATH your interactive shell has, in its order, rather than a login shell's: `zsh -l` sources `.zprofile` but not `.zshrc`, and nvm lives in `.zshrc`, so the app and the terminal were resolving different programs by the same name. And the four agents that ship their own updater — Claude, Grok, Cursor, Hermes — get a button at last: they had none, because the only thing that produced one was a version comparison they could not take part in. Where a version genuinely cannot be known in advance, Uncoil offers "Check & Update" and says nothing it has not checked; only a version it has actually seen counts towards the badge.

- New sessions no longer open onto a terminal that never prints anything. A session's keystrokes were written straight to its terminal, and a terminal only holds a few kilobytes of input before it makes the writer wait for the program to read some. An agent that stopped reading for a moment — one busy in a long tool call, one that had been paused — was enough: the write never returned, and it was made on the one queue inside the background service that also carries every other session's output and every command Uncoil sends it. Everything stopped at once. Because that service deliberately outlives the app, so agents survive a restart, quitting Uncoil and opening it again found the same stuck service and connected to it: every new session, Claude or Codex alike, came up blank and stayed blank, while the same CLI in Terminal.app was fine. In practice only rebooting cleared it. Input the terminal cannot take now waits its turn instead of stopping the service, and three things back that up: the service's daily scan runs where it cannot block anything, having previously been able to hang the whole service with the timeout meant to end it queued behind the hang; Uncoil's own end of the connection no longer waits on a service that has stopped listening, so the heartbeat that watches for exactly that can still run; and a service that accepts a connection and then says nothing for ten seconds, twice, is ended and started again rather than reconnected to forever.

- The settings sidebar stays where you left it when you change the theme. Uncoil re-identifies its views when the palette changes, because the colours are read in a way SwiftUI cannot track on its own — but that key was attached to the whole settings window, so it rebuilt the source list too and threw it back to the top: exactly where you were standing when you changed the theme, since that is the page the control is on. It is now attached to the page being shown, which is the part that needed it.

- Uncoil no longer disagrees with itself about which CLIs are installed. It had three separate lists of where to look for an agent binary — one for launching a session, one for the Extensions screen, one per usage probe — and they held different directories, so a CLI installed under `~/.volta/bin` was visible on one screen and missing on another, and one under `~/.npm-global/bin` the other way round. There is one list now, and finding a CLI the list does not cover no longer costs a login shell per lookup: the shell's own `PATH` is read once per run instead of once per question, which is what made asking about seven agents slow.

- Agent marks stay visible in the light theme. The marks for OpenCode, Grok, Cursor and Amp were fixed colours rather than palette entries, which is fine on a dark background and not on a light one: Grok's own white measured 1.00:1 against the white panel — the mark was not faint, it was absent — and the other three sat between 1.03 and 2.54 where the app holds everything else to 3. They are palette entries now, inverted rather than dimmed for the light preset, and the contrast test covers every agent mark instead of two of them.

- Gemini's blue is readable on a light background. It never had a light value of its own, and nothing checked it until every mark was brought under the contrast test: the shipped blue measured 2.92:1 on a hovered panel, under the same floor Claude's and Codex's colours were darkened for.

- Sessions no longer freeze, and a frozen one no longer takes the app with it. Two faults in the runtime daemon, both of which ended the same way: a session that stopped responding, a restart button that did nothing about it, and processes left behind to be killed by hand. The first is that the daemon wrote a session's replay to disk on *every* chunk of output — half a megabyte at a time, 8.5 GB in half an hour of ordinary use — on the same queue it uses to carry every session's output and answer every command, so restarting a session meant waiting behind a backlog of disk writes. The replay is now written on a timer, which is all a file nobody reads until the app restarts ever needed. The second is that the daemon wrote to the app with a blocking call: if the app stopped reading for a moment, the socket filled and the daemon stopped inside that write — every session, every command, at once. It now queues what the app cannot take yet, and drops a client that never catches up instead of waiting on it forever.

- Reading a Claude account's limit asks the CLI first, and stops asking for your password. Uncoil went to Anthropic's API first, which meant finding a credential of its own — and when the one on disk was not there it went to the Keychain, where macOS asks before handing another application's login over. On a five-minute timer that is a password prompt five minutes apart, and it never settles during development because the answer is recorded against a signature every rebuild changes. The installed `claude` reads its own login, so it asks nobody anything, and the account it answers for is by construction the one you are working with rather than whatever the found credential belonged to. The API is still there, behind it, for a machine with no CLI installed.

- Uncoil no longer crashes after hours of being left open. Reading Claude's usage panel waits on a file descriptor, and the bit that marks which one to wait on was written in a way that trapped whenever the number the system handed out was 31, 63, 95 and so on — reachable only after enough files had been opened and closed, which is why it took an afternoon of ordinary use to arrive. Descriptors past the end of the set are now refused instead of written past it.

- Picking a filter on a collapsed suite opens it. Choosing what to look at was changing a list nobody could see.
- The Tests screen's `All` filter shows every step again. On a run with failures it fell straight back to the failures, because "the user chose All" and "the user has chosen nothing yet" were the same state internally, and the second one means "lead with what failed".

### Changed

- The changes panel is gone from the session view. It listed the working directory's changed files and its last few commits beside the terminal — a summary of what the agent had done that was quicker to get from the agent itself, or from the project screen, which shows the same thing. Diffs were never in it and are unaffected: they are still on the task screen's Show Diff and in the merge screen.

### Fixed

- Three ways a task file could silently lose tasks are closed. A code fence that never closed — a typo, or a ``` answered with `~~~` — used to run to the end of the file and take every task after it: they disappeared from the app while still sitting in the file. A fence now holds only if it closes, which is the same reading unterminated frontmatter already got. A `#` written inside a task's description — a shell comment, an issue number, a Markdown example — was read as a heading however deeply it was indented, which cut the task's text off at that line and rewrote the section every task below it belonged to; indentation now decides what belongs to a task, for that line as for every other. And a rule written straight under a paragraph is read as the rule it looks like, instead of turning the paragraph's last line into a heading — that one mattered beyond appearances, because a task's section is part of its identity, so everything below the rule changed identity at once and lost the session assignments and board placement saved against it.
- Editing a task's description no longer flattens it. The writer stripped every line's own indentation and deleted every blank line, so a description holding a code fence, a nested list or a paragraph break came back from an edit as one flat run — written to the file, where the structure could not be recovered. A body is now shifted into place rather than reflowed: whatever indentation all its lines share is replaced by the block's, and everything between them survives. The same fault made an agent adding a single note rewrite the whole description; a note is now appended to the body exactly as it stands.
- A task is shown as the sentence it is, not as its first physical line. Task files are written to a column width, so a long task is one sentence broken across several lines — and Uncoil read only the first of them, which is why most tasks appeared to stop mid-sentence. The lines that are only that sentence continuing are now read as part of it and drawn as one wrapped paragraph; in this project's own list that is 107 of 146 tasks. What the file says on the task's own line is untouched, so renaming and every other patch still land exactly where they did.
- What a task says beyond its sentence — a nested list, a fenced example, a second paragraph — is reachable everywhere. It used to live in the document view only, behind a chevron, and nowhere at all in the list. Every list row has that chevron now, and the body is selectable text. Tasks that are only a wrapped sentence no longer offer one, because there is nothing behind it.
- The Tasks screen scrolls smoothly with a long list. Four things were being redone on every redraw of a screen that redraws for anything: the Markdown marks were stripped from every visible row by compiling ten regular expressions per row, per pass; each row scanned every assignment in the project twice and each board card filtered *and sorted* up to five hundred stored results; the heading-and-task interleave was re-sorted for every file; and the board and session views built every row eagerly instead of only the visible ones. All four are now done once and reused.
- Typing in the task search field no longer stalls. Every keystroke fuzzy-scored every task in the project and re-laid out the whole screen; the field stays immediate and the work it causes waits for a pause in the typing.
- A `TODO.md` created in a subdirectory that had none is noticed straight away. The watcher could only watch files that already existed, so a new task file stayed invisible until something else forced a rescan. One filesystem-event stream now covers the project, and it ignores everything that is not a task file — a build writes thousands of files a second and none of them can change what your tasks are.
- A project's own `TODO.md` is found even when git is told to ignore it. Scanning followed the project's `.gitignore`, and a task list is very often kept out of the history on purpose — so the file a project actually plans its work in was the one file Uncoil refused to show. Ignore rules are no longer consulted, files in nested git repositories count as the project's own, and the depth limit is generous enough for a repository inside a monorepo inside a project. What is still skipped is only what cannot hold your tasks: dependency trees and tool caches, by name. `build`, `dist` and `target` left that list — they are as often somebody's own source directory as generated output, and a wrongly skipped file is invisible rather than merely unwanted.
- The sidebar stops calling running agents closed. A session's status lives in memory while the agents themselves live in a daemon that outlives the app, so every session restored at launch had no status — and a missing status was read as "Closed". The app spent the first moment of every launch reporting that your agents had stopped, and went on saying it forever if the daemon never answered. "Not known yet" is now a state of its own, shown as such, and it lasts about a second.
- A daemon hiccup no longer closes every running agent. The daemon is asked once, at the handshake, what it still has; a session left out of that one answer was written to disk as ended, permanently, with no way back — including when the daemon answered while restarting, before it had re-adopted the sessions it still owned. A session missing from one answer is now shown as not yet known and asked about again; only the second silence closes it.
- Gemini sessions no longer show another agent's work. Gemini reports nothing and never binds a session id, which made it the standing fallback for every Claude event that named no session — so a row that had done nothing announced that it was running or waiting for permission. Events are only ever guessed onto a session whose agent reports through hooks at all.
- A session whose record says it ended can no longer keep claiming it is working. Reconciliation skipped ended records entirely, so that disagreement was the one direction nothing corrected.
- The app icon follows the system appearance. In dark mode the Dock showed the light icon — a white tile, at full brightness, next to everything else that had gone dark. The cause was that both the light and the dark artwork had their background painted into the image, and macOS 26 composes an icon the other way round: the app supplies the artwork, the system supplies the background per appearance. The spiral is now a single layer with nothing behind it, recovered exactly from the two existing images, so light, dark and tinted are all drawn from the same one.
- The sidebar no longer reshuffles its sessions while you work. A session that had never been dragged was placed by when it was last active, so every reply from an agent moved its row — usually to the top, usually while the cursor was already on its way to another one. Order is now fixed when the session is created: new sessions join the end of the list, existing ones keep the order you last saw them in, and nothing moves again unless you move it.

## [0.1.0] - 2026-08-04

First public beta. Everything Uncoil does today ships in this release — the
dated sections at the end of this file are development entries from before the
project was versioned, and they are part of 0.1.0 too.

### Added

- Uncoil is free software, published under the Apache License 2.0 with a README that explains what it is and how to build it. The only dependency is SwiftTerm (MIT), and the build instructions no longer point at one particular Mac's disk.
- Real multi-window support. ⌘N already opened a second window, but every window read the same stored selection and fought over it; a window now takes an identity when it appears, keeps its own selection and split pane, remembers its frame under a name of its own, and gives everything back when it closes. Opening one by hand asks what it should open on — clone the main window, clone a named window, or start empty — and a clone opens on the source's project and view rather than its session. The arrangement comes back at launch, and quitting is told apart from closing so the last window out does not record a single-window app.
- Settings › CLI Tools answers "what is on this Mac" in one place: per agent, how it was installed, its version, the path on `PATH`, what that path resolves to, and the exact command an update would run. The resolved path is the part that matters — the launcher is nearly always a symlink, and which install a tool belongs to is only visible at the other end of it. "Up to date" is no longer shown before both halves of the comparison are in.
- The project list belongs to the window. An empty window is empty including its sidebar, and a project opened in one window is in that window; its empty sidebar lists the projects the app has and this window does not, one click each, so a clean window is not a dead end. Windows that predate this — the one you already had, and every window restored from an older version — go on showing every project, including ones added later.
- A session is shown in one window at a time, and the others say so. This was already true of the machinery and not of the interface: one `TerminalView` exists per session, an `NSView` has one superview, and a second window mounting the same terminal took it out of the first silently, mid-render. Selecting a session claims it, navigating away gives it up, and claiming never steals — a window that does not have it draws "This session is open in another window" where the terminal would be, names the window that does, and offers both answers: go there, or move it here. Dragging a terminal into a popout still takes it, because someone who did that meant to, and the popout is a window under the same rule.

### Fixed

- Updating an agent CLI installed through a Node version manager works. Reported as "Gemini shows an update but updating fails", and it was three defects at once: install detection asked for substrings that a path like `~/.nvm/versions/node/v24.1.0/bin/gemini` does not contain, so it read as unknown; there was no Gemini update command at all beyond the Homebrew one; and the Homebrew command used the tool's own name, while Homebrew calls them `gemini-cli` and `claude-code`. Detection now follows the symlink — a global npm package always lands under `lib/node_modules` whoever manages the Node — and runs that Node's own npm, so the update goes back where the binary came from rather than into whichever Node the login shell happens to resolve. An install that still cannot be placed says so instead of guessing.
